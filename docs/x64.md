# 64-bit (x86_64) Windows build

The x64 build uses clang from llvm-mingw. Game code keeps the GameCube's
32-bit data layouts: pointer fields of disc-layout structs are clang
`__ptr32` pointers (`DPTR`), and all game memory lives below 4 GiB, so a
32-bit field can still hold any game address. The 32-bit build (GCC,
`cmake/mingw32.cmake`) is unaffected, and the GC build of the decomp stays
byte-identical because every macro below expands to nothing (or to the
32-bit type) there.

Before changing pointer-sized data, read the
[checklist](#checklist-for-pointer-size-changes) below.

## Build

```
# once: unpack llvm-mingw-20241217-ucrt-ubuntu-20.04-x86_64.tar.xz (GitHub mstorsjo/llvm-mingw)
cmake -G Ninja -S pc_port -B build64 -DCMAKE_TOOLCHAIN_FILE=$PWD/pc_port/cmake/llvm-mingw64.cmake \
      -DLLVM_MINGW_ROOT=$PWD/toolchains/llvm-mingw-20241217-ucrt-ubuntu-20.04-x86_64 \
      -DSMB2_DECOMP_DIR=$PWD/decomp -DSMB2_GAME=ON
ninja -C build64
```

GCC x64 is rejected (`FATAL_ERROR` / `#error`): it has no `__ptr32`.

## Why `__ptr32`

Disc files (stagedefs, NL models, GMA/TPL, ape archives, scenes, dialogs,
replays) are used in place: the game loads the file and turns offsets into
pointers inside the loaded image. Static data tables and literal sizes in the
decomp assume 4-byte pointers as well. Translating every format into native
64-bit structs at load time would need a converter per format and changes at
thousands of dereference sites.

`T * __ptr32 __uptr` is a 4-byte, 4-aligned pointer that zero-extends on
load and converts implicitly to and from normal pointers. Field reads,
writes, `->`, `[]`, `++` and comparisons compile unchanged, so only the field
declarations change. The memory card and `.rec` replay layouts stay the same
as on 32-bit without a serializer.

The cost: the x64 build needs clang, and it depends on all game memory being
below 4 GiB. A port to a platform where the low 4 GiB is unavailable (macOS
arm64 reserves it as `__PAGEZERO`) would need native layouts instead.

## Memory

- The exe is linked at a fixed image base of 0x10000000, with no dynamicbase
  and no high-entropy VA. Code and statics are below 2 GiB.
- GC RAM is reserved at 0x80000000 by a constructor in gc_mem.c, before
  SDL/GL/D3D load (a GPU driver can otherwise take the range). The x64 build
  exits if the range can't be mapped.
- `pc_check_address_space()` prints where the image, stack, malloc and GC RAM
  landed, and exits if the image or GC RAM is above 4 GiB.
- The CRT heap is also low in practice, but nothing guarantees that.
  **Never store a malloc'd host pointer in a DPTR field.**
- Absolute GC addresses such as `*(u32 *)0x800000F8` work because GC RAM is
  mapped at exactly 0x80000000.

## Types (`decomp/include/types.h`)

| Type / macro | GC and 32-bit | x64 | Use for |
|---|---|---|---|
| `DPTR` | empty | `__ptr32 __uptr` | Pointer fields of structs whose 32-bit layout must hold: disc/file images, static word tables, and structs allocated or cleared with literal sizes, **if** all their pointees live in GC RAM or the exe. Write `T * DPTR f;` and `T * DPTR * DPTR f;`. A local that walks a DPTR array is `T * DPTR *p`. |
| `uptr` / `sptr` | `unsigned int` / `int` | 64-bit | Integer fields and globals that hold pointers. Use `sptr` for **signed** ones: GC RAM addresses are ≥ 0x80000000, so an s32 round trip sign-extends them to 0xFFFFFFFF8xxxxxxx. |
| `PC_PTR_SCALE` | 1 | 2 | Raw `u8 buf[N]` buffers that hold arrays of pointer-bearing structs. |
| `PC_A32(x)` (`pc_addr32.h`) plus generated fixups (`tools/gen_addr32_fixups.py`) | `(u32)(x)` | 0, stored at startup | Address words inside u32 data tables (on x64 an address is not a constant initializer for a u32). |

`include/pc_ptr32.h` is force-included first in every x64 TU: mingw-w64's
`_mingw.h` does `#define __ptr32` (empty, for GCC), which would silently turn
DPTR into a plain 8-byte pointer.

DPTR is used by: all `Stage*` structs (stage.h); NlObj, NlObj_UnkChild,
NlMesh.texObj, NlModelHeader; GMA, GMAModelEntry, GMAModel.texObjs, the GMA
TEV layer views, TPL; ApePartEntry/List, ApeModelTable/Entry, ApeData,
ApeClipInfo, ApeClipGroup; Mta; Replay* in recplay.c and cmp_recplay.c;
scene and dialog images, Dialog/TextBox; the ARC handle shims; and the PC
mirrors PcGMA, PcGMAEntry, PcTPL.

Formats that need no DPTR: the MusyX sound banks (musyx_shim.c parses them
into its own structs), the ApeMal clip catalogs (offsets stay u32 and are
converted at the use site), and TPL texel data (`imageOffset` is an offset).

## Pitfalls

Layout mistakes compile cleanly and fail at runtime, often far from the
cause. The patterns to look for:

- **Literal sizes.** `memset`/alloc sizes, `ord_tbl_alloc_node(0xC)`, `n * 12`,
  `<< 2` for pointer arrays, qsort element sizes of 4 for pointer arrays, and
  hard-coded offsets past a pointer field (`ape + 0x258`). Use `sizeof`,
  `offsetof` or the field. A struct that keeps a literal size needs DPTR
  fields so that its size matches.
- **Overlays with GC offsets.** A local struct or `u8 filler[0xC]` that views
  another struct (TEV callback arguments, effect views of Instance, ape
  animation through `struct ApeAnim`) breaks when the real struct grows.
  Use the real struct. The same goes for a struct that a cast puts over
  another one: `struct SpriteTexture` (what `draw_texture_sprite` reads) is
  really a `struct Preview`, and its `u8` pad over Preview's `imagePtr`
  made the texture-sprite previews (Monkey Fight/Dogfight/Baseball/Tennis
  stage select, replay list) 0 pixels high on x64 until 1.1.12. Declare the
  shared fields with the real types and `_Static_assert` their offsets. `struct ApeAnim` is incomplete on purpose; ape
  animation state is accessed as `struct Skeleton` (`APE_BODY()` etc.).
- **Pointers in s32.** Any `s32`/`int` that stores a pointer must be `sptr`
  (heap handles, `Ape.unk0`/`unk14`, function pointers in s32 fields).
- **Cross-TU declarations.** A global defined as `u32 x` in one TU and
  declared `extern T *x` in another makes an 8-byte access to a 4-byte
  object. Define it as `uptr` or with the real type
  (`tools/x64test/crossdecl.py` finds these).
- **Shim mirrors.** PC code that mirrors a decomp struct as bytes (e.g.
  `struct PcFile { u8 raw[...]; }` for `struct File`) must allow for the x64
  size and check it with `_Static_assert`.
- **Generated stubs.** `stubs_gen.c` sizes data blobs from the GC symbol maps
  times `PC_STUB_SCALE`, and returns pointers and doubles from typed stubs. A
  stub must not replace a tentative definition in a decomp TU, which has the
  real x64 size.
- **Missing prototypes.** An implicitly declared function returns `int`, which
  truncates a returned pointer (`getenv`, `GXGetTexObjData`).
- **Preprocessor tests.** `#if UINTPTR_MAX ...` without `<stdint.h>` silently
  evaluates to 0; use `__SIZEOF_POINTER__`.
- **Clang 19 limitations.** It cannot call through a `__ptr32` function pointer
  ("Cannot select X86ISD::CALL"): cast to a native function-pointer type
  first. It also fails instruction selection on a DPTR load through a DPTR
  base inside `?:` ("Cannot select ... bitcast"); use a local. Both are loud
  compile-time failures. `T **local = s->dptrArray` is an error ("changes
  address space of nested pointer"); spell it `T * DPTR *`.
- **Out-of-range float→integer casts** behave differently under clang; see
  [detmath.md](detmath.md).

## Memory card and replay compatibility

Replay (`rep*.dat`) and game data (`super_monkey_ball_2.dat`) files written
by the x64 build have the same layout as the 32-bit build's, and each build
loads and plays the other's files. `tools/x64test/card_xarch.sh <bin32>
<bin64> [gl|d3d12]` checks this. Game data is byte-identical apart from the
card timestamp. Replay streams decode identically; bytes the game never
writes (0x44-0x5F and after the stream end) may differ.

## Debugging and tools

- The x64 crash handler prints the full 64-bit registers.
- `-gline-tables-only` is on, so a crash dump symbolizes with:
  ```
  (grep -o 'rip=[0-9A-F]*' log | sed s/rip=/0x/; grep -o 'stack\[[0-9]*\] 10[0-9A-F]\{6\}' log | awk '{print "0x"$2}') \
    | $LLVM_MINGW_ROOT/bin/llvm-symbolizer --obj=build64/bin/smb2_pc_port.exe
  ```
  The stack-scan frames are heuristic.
- `-DSMB2_PTR_WARNINGS=ON` enables `-Wpointer-to-int-cast` and
  `-Wint-to-pointer-cast` for the game TUs. Most reported casts are safe
  below 4 GiB; the ones to fix store pointers in signed types.
- `SMB2_HEAP_CHECK=1` (os_shim.c): a guard and the allocation site on every
  heap block, all heaps checked on every alloc/free. Reports the first
  overrun block or corrupt free cell with the `alloc_from_heap_or_panic`
  file:line, then exits 3. The fastest way to find x64 size bugs; the 32-bit
  build runs clean with it.
- `tools/x64test/structsizes.py <decomp> <llvm-mingw>`: decomp header
  structs whose size differs between i686 GCC and x64 clang (table below).
  One that lives in disc data, a static table, a literal-size alloc/memset
  or an overlay is a bug: fix it with DPTR or sizeof.
- `tools/x64test/crossdecl.py <decomp> <pc_port/src>`: globals defined as an
  int or byte array but declared as a pointer or struct elsewhere. Entries
  already widened to `uptr`/`sptr` are listed too and are fine. Known
  remaining entries: `lbl_1_bss_12AC` (u8[0x2C] vs struct ExOptionFile); the
  mot_ape.c u32 globals vs test_mode pointers (test_mode isn't built).
- `tools/x64test/modes.sh`: runs the same input script on any build and
  renderer, diffs the frame dumps and writes comparison sheets. x64 and
  32-bit runs differ only where two 32-bit runs also differ (CPU players and
  effects seeded from `OSGetTick`, attract camera, particles). Don't run more
  than about two exes at once on WSL.

## Checklist for pointer-size changes

- **GC build stays byte-identical.** Run
  ```
  cd decomp && python3 configure.py && ninja && dtk shasum -c config/GM2E8P/build.sha1
  ```
  (`dtk` is downloaded to `build/tools/dtk`) and expect 21 OK. PC-only code goes inside
  `#ifndef __MWERKS__`, or uses the types.h macros, which are identical on GC.
- **The 32-bit build must keep working.** Check it with `modes.sh` on GL and D3D12.
- **Choosing a fix.** Pick the smallest change that keeps the GC layout:
  1. A struct whose layout is fixed by disc data, a static table, a literal
     size/offset or an overlay, and whose pointees all live in GC RAM or the exe:
     add `DPTR` to its pointer fields. Change any `T **` local that walks a DPTR
     array to `T * DPTR *`.
  2. An integer field or global holding a pointer: use `uptr`. Use `sptr` where
     it was signed — GC RAM is at 0x80000000, so an s32 round trip sign-extends.
  3. A raw byte buffer holding pointer-bearing structs: `PC_PTR_SCALE`.
  4. Address words in a u32 table: `PC_A32()` plus `pc_port/tools/gen_addr32_fixups.py`.
  5. Host memory (CRT malloc, renderer objects) must **never** go into DPTR or u32.
- **Test** with the harness (`tools/x64test/modes.sh`; see its header for
  `SMB2_X64_WS`, `SMB2_ISO`, `tools/ppmtool` and `tools/memcard_pristine`).
  Runs only write below `$SMB2_X64_WS` and always pass `--save-dir`.
  ```
  T=pc_port/tools/x64test/modes.sh
  $T gl32 $WS/build32/bin <modes> -- --renderer gl
  $T gl64 $WS/build64/bin <modes> -- --renderer gl
  $T dx64 $WS/build64/bin <modes> -- --renderer d3d12
  $T --compare gl32 gl64 dx64 <modes>     # sheets in $WS/runs/sheets/gl32_vs_gl64_dx64/<mode>/
  ```
  Frames past the attract demo aren't deterministic, so judge the sheets
  visually. Crashes in a dump symbolize with llvm-symbolizer (Debugging and tools, below).
- **Before committing:**
  - the affected modes run on x64 GL and D3D12 for the whole script, with no
    crash and no watchdog;
  - sheets match 32-bit apart from known nondeterminism;
  - GC is 21 OK and 32-bit is unchanged;
  - no new pointer-cast warnings (`-DSMB2_PTR_WARNINGS=ON`).
